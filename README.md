## 2. SLO тодорхойлолт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 50 ms | 20 VU тогтмол ачаалал, 1 минут |
| Reliability | `/pay` error rate | < 8% | 20 VU тогтмол ачаалал, 1 минут |
| Availability | Амжилттай хүсэлтийн хувь | ≥ 90% | 2 минутын туршилт, 10 секундийн зогсолт |
| Нэмэлт Performance | `/report` latency | p95 < 450 ms | 20 VU тогтмол ачаалал, 1 минут |

### Босго сонгосон үндэслэл

**Performance:** `/cart/add` нь нэмэлт боловсруулалтын сааталгүй локал endpoint тул p95 хариу хугацааг 50 ms-ээс бага байхаар сонгосон.

**Reliability:** `/pay` endpoint-д зориудаар ойролцоогоор 5% алдаа үүсгэдэг тул хэвийн хэлбэлзлийг тооцож error rate-ийн босгыг 8%-иас бага байхаар сонгосон.

**Availability:** Chaos туршилтын 2 минутын цонхонд серверийг 10 секунд зогсоох тул availability-г хамгийн багадаа 90% байхаар сонгосон.

**Нэмэлт Performance:** `/report` endpoint нь зориудаар 200–400 ms сааталтай тул p95 босгыг 450 ms-ээс бага байхаар сонгосон. Энэ нь endpoint-ийн төлөвлөсөн саатлаас бага зэрэг нөөцтэй боловч хэт сул биш босго юм.

### Error budget

Availability SLO = 90%

Error budget = 100% - 90% = 10%

2 минут = 120 секунд

120 × 10% = 12 секунд

Иймээс 2 минутын туршилтын хугацаанд системийн цаг хугацаагаар тооцсон error budget нь **12 секунд** байна.
## 3. Chaos туршилтын үр дүн

Availability-г шалгахын тулд k6 тестийг 20 VU ачаалалтай 2 минут ажиллуулж, тестийн явцад API серверийг 10 секунд зогсоогоод дахин асаасан.

- Нийт хүсэлт: 5709
- Амжилттай хүсэлт: 4870
- Амжилтгүй хүсэлт: 839
- Request-based availability: 4870 / 5709 × 100 = 85.30%
- Availability SLO: ≥ 90%
- Үр дүн: FAIL
- `/pay` error rate: 17.81%
- Reliability SLO: < 8%
- Үр дүн: FAIL

### Error budget-ийн харьцуулалт

2 минутын туршилтын хугацаа 120 секунд. Availability SLO 90% учраас error budget нь 12 секунд байна. Серверийг 10 секунд зогсоосон тул time-based хэмжилтээр 10 секунд нь 12 секундийн error budget дотор байна.

Гэхдээ request-based availability 85.30% болсон тул request-based SLO хангагдсангүй. Сервер унтарсан үед connection refused хариу маш хурдан үүсдэг тул богино хугацаанд олон failed request бүртгэгдсэн. Иймээс time-based availability болон request-based availability хооронд ялгаа гарсан.

Chaos туршилтын үед `/pay` error rate 17.81% болж reliability threshold мөн FAIL болсон. Учир нь `/pay`-ийн зориудын алдаанаас гадна сервер унтарсан үеийн хүсэлтүүд мөн failed request болж бүртгэгдсэн. Availability болон reliability-г илүү зөв тусгаарлахын тулд серверийн хүрэлцээтэй байдлын алдаа болон `/pay` endpoint-ийн application error-ийг тусдаа metric/tag-аар хэмжиж болно.
## 4. Зориудаар FAIL болгосон туршилт

Threshold зөрчигдөх үед k6 хэрхэн FAIL төлөв болон non-zero exit code буцааж байгааг шалгахын тулд тусдаа `slo-test-fail.js` файл үүсгэсэн.

`/report` endpoint нь 200–400 ms сааталтай ажилладаг тул түүний threshold-ийг зориудаар:

`p(95) < 100 ms`

болгож чангаруулсан.

Туршилтын үр дүн:

- `/report` p95: 390.43 ms
- Threshold: p95 < 100 ms
- Үр дүн: FAIL
- k6 exit code: 99

Бусад threshold-ууд:
- Checks: 98.12% → PASS
- `/cart/add` p95: 2.71 ms → PASS
- `/pay` error rate: 5.61% → PASS

Ингэснээр SLO threshold зөрчигдөх үед k6 тестийг автоматаар FAIL болгож, non-zero exit code буцааж байгааг баталсан. Энэ механизмыг CI/CD pipeline-д чанарын шаардлага хангаагүй build эсвэл deployment-ийг илрүүлэхэд ашиглаж болно.

## Нэмэлт даалгавар – AI ашигласан шинжилгээ

`server.js` кодыг ChatGPT-д өгч, 6 хэсэгтэй форматаар Performance, Reliability, Availability гэсэн 3 чанарын сценарио гаргуулсан. AI Performance сценариод `/cart/add` endpoint-ийн p95 хариу хугацааг 200 ms-ээс бага, Reliability сценариод `/pay` error rate-ийг 10%-иас бага, Availability сценариод availability-г 99%-иас дээш байлгах босго санал болгосон. Манай локал туршилтаар `/cart/add`-ийн p95 2.40 ms байсан тул AI-ийн 200 ms босго хэт сул, харин `/pay`-ийн бодит error rate 4.64% байсан учраас 10%-ийн босго мөн харьцангуй сул гэж үзсэн. Availability-д санал болгосон 99% нь серверийг зориудаар 10 секунд унтраах манай chaos туршилтын нөхцөлд бодитой биш байсан бөгөөд бид 2 минутын туршилтад 90%-ийн SLO сонгосон. AI нь `server.js` кодоос серверийг зориудаар 10 секунд зогсоож дахин асаах өдөөлтийг мэдэх боломжгүй тул availability сценариод энэ өдөөлтийг өөрөө тодорхой тусгаагүй. Харин AI-ийн гаргасан сценарио нь 6 хэсгийн бүтцийг тодорхой ялгаж, чанарын шинж бүрийг хэмжигдэхүйц үзүүлэлттэй холбосон нь сайн тал байсан. Өөрийн бичсэн сценарио нь бодит k6 туршилтын ачаалал, 20 VU, 1–2 минутын хугацаа болон 10 секундийн серверийн зогсолтыг тусгасан учраас тухайн системийн бодит туршилтын нөхцөлтэй илүү нийцсэн гэж дүгнэсэн.
## 5. Дүгнэлт

Энэхүү лабораторийн ажлаар программын чанарын сценариог хэмжигдэхүйц SLO болгон тодорхойлж, k6 threshold ашиглан автоматаар шалгаж сурлаа. Сценариог SLO болон threshold болгон шилжүүлэхэд хамгийн хэцүү нь системийн бодит ажиллагаанд тохирсон, хэт сул эсвэл хэт хатуу биш тоон босго сонгох байсан. Performance туршилтаар `/cart/add` endpoint-ийн p95 хариу хугацаа 2.40 ms гарч, 50 ms-ийн SLO босгыг хангасан. Reliability туршилтаар `/pay` endpoint-ийн error rate 4.64% гарч, 8%-ийн босгыг хангасан. Мөн `/report` endpoint-ийн p95 хариу хугацаа 391.46 ms гарч, 450 ms-ийн нэмэлт босгыг хангасан. Chaos туршилтын үед серверийг 10 секунд зогсооход request-based availability 85.30% болж, 90%-ийн SLO-г хангаагүй тул availability сценариогийн хэмжүүр бодит доголдлын үед хэрхэн өөрчлөгдөхийг туршилтаар баталгаажуулсан. Харин time-based error budget 12 секунд байсан тул 10 секундийн зогсолт нь хугацааны хувьд error budget дотор байсан. Энэ нь time-based болон request-based availability хэмжилтүүд өөр үр дүн үзүүлж болохыг харуулсан. Зориудаар `/report` threshold-ийг p95 < 100 ms болгож чангаруулахад тест FAIL болж, k6 exit code 99 буцаасан. Ерөнхийдөө чанарын шаардлагыг сценарио → SLO → threshold гэсэн дарааллаар бодит хэмжүүртэй холбож, автомат тестээр баталгаажуулах нь системийн чанарыг үнэлэхэд чухал болохыг ойлгосон.
